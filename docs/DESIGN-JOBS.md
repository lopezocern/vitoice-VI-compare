# 执行型工具设计：视频优化器 / EXIF 移除器

> 这两类工具和前 10 个工具的本质区别：**它们不产出「待删除列表」，而是产出「新文件」**。
> 所以不能用「扫描 → 结果 → 隔离」的模型，要换成 **配置 → 预估 → 执行 → 报告** 的作业模型。

---

## 1. 为什么不能复用结果页

| 维度 | 扫描型（已有 10 个） | 执行型（本次） |
|---|---|---|
| 用户目标 | 找出可以删的 | 把文件变小 / 去掉隐私 |
| 输出 | 一份判定结果 | 一批新文件 |
| 失败代价 | 误删（可恢复） | 转码失败 / 画质崩 / 覆盖原片 |
| 关键交互 | 对比、勾选、隔离 | 参数、预估、进度、回滚 |

核心风险从「删错了」变成「转坏了」和「原文件没了」。所以设计的第一原则是：

> **永远不原地覆盖。** 输出到独立目录，原文件保持不动，满意后由用户自己决定是否用优化版替换。

---

## 2. 作业模型（四段式）

```
① 选源        ② 配置预设        ③ 预估        ④ 执行 & 报告
  文件/目录  →  3 个预设 + 高级  →  体积/耗时  →  队列 + 进度 + 撤销
```

**③ 预估必须前置。** 用户最关心的是「能省多少、要等多久」，这两个数字必须在点下「开始」之前给出来，否则没人敢点。

---

## 3. 视频优化器

### 3.1 预设（覆盖 90% 场景）

| 预设 | 分辨率上限 | 编码 | 质量 | 典型场景 |
|---|---|---|---|---|
| 社交分享 | 1080p | H.264 | CRF 23 | 发抖音/微博，兼顾体积与画质 |
| 长期存档 | 原分辨率 | H.265 | CRF 20 | 留底，体积减半画质几乎无损 |
| 极致压缩 | 720p | H.264 | CRF 28 | 只求能看，体积优先 |
| 自定义 | 手动 | H.264/H.265 | 手动 CRF | 参数党 |

**预设卡片要直接标出「预计节省 60–75%」这类结论**，而不是只列 CRF 数字。

### 3.2 预估算法

```
输出体积 ≈ 时长 × (目标码率 + 音频码率) / 8
耗时     ≈ 源体积 / 基准速度(本机实测, 默认 18 MB/s) × 并发系数
```
- 源文件已经是 H.265 且分辨率低于目标的 → 标记「无需优化」并跳过。
- 预估误差超过 20% 时，报告里要如实标注「实际与预估有偏差」。

### 3.3 高级参数（折叠）

分辨率上限 / CRF / 编码器 / 音频码率（或移除音轨）/ 保留字幕 / 硬件加速开关。

> 实测数据：本机 CUDA 转码反而比软件慢（短文件 CUDA 上下文初始化约 0.8 秒），
> 所以**默认走软件 x264/x265**，硬件加速放在高级里默认关闭。

### 3.4 执行与安全

- 输出目录：`<源目录>\_optimized\`，保留相对路径结构。
- 同名冲突：追加 `_v2` 而不是覆盖。
- 断点：每个文件完成即写一条记录，崩溃后可从断点继续。
- 撤销：整批输出移到隔离区（复用现有 manifest 机制），不删原片。

## 4. EXIF 移除器

### 4.1 与视频优化器的差异

EXIF 的「参数」不是码率，而是**保留哪些元数据字段**。所以配置区变成一张**字段清单**：

| 字段 | 默认 | 说明 |
|---|---|---|
| 相机型号 / 镜头 | 移除 | 隐私风险低，但可识别设备 |
| GPS 坐标 | **移除（强制）** | 隐私风险最高 |
| 拍摄时间 | 保留 | 整理照片依赖它 |
| 软件 / 序列号 | 移除 | 可追踪 |
| 方向 Orientation | 保留 | 移除会导致图片旋转错乱 |
| 缩略图 | 移除 | 重新生成 |

### 4.2 关键设计点

- **元数据预览**：选中文件后，先展示「这个文件里到底有什么」，让用户看见 GPS 那一行，再决定删不删。这是隐私工具最有效的说服方式。
- **Orientation 必须保留**，否则图会歪 —— 要在界面上明确写出「为什么不能删」。
- 仅支持 JPEG/PNG/WebP/TIFF；HEIC/RAW 标记为不支持。

### 4.3 输出策略

| 选项 | 说明 |
|---|---|
| 输出到 `_clean\`（默认） | 原文件不动，最安全 |
| 覆盖原文件（自动备份） | 写入 `_backup\` 后再覆盖，适合批量整理 |

## 5. 队列与进度

两类工具共用一个作业队列：

```
[文件 A]  42.1 MB → 12.3 MB   ████████░░ 78%   1.2x 实时
[文件 B]  18.4 MB → 预估 5.1 MB  等待中
[文件 C]  已是 H.265           已跳过
```

- 顶部总进度：`68% · 剩余 1 分 20 秒 · 11/16 个文件`
- 支持暂停 / 取消（当前文件跑完再停，避免产出半截文件）
- 失败项单独列出，附 ffmpeg 错误首行，可单独重试

## 6. 接口草案

```rust
struct JobPlanRequest { tool: String, paths: Vec<String>, preset: String, options: Json }

struct JobPlan {
    files: Vec<PlannedFile>,     // 每个文件的预计输入/输出
    total_in: u64,
    total_out: u64,
    eta_secs: u32,
    warnings: Vec<String>,       // 「3 个文件已是 H.265」「2 个不支持」
}

struct PlannedFile {
    src: String, out: String,
    in_bytes: u64, out_bytes: u64,
    action: Action,              // Optimize | Skip | Unsupported
    reason: String,
}

// 命令
plan_job(req) -> JobPlan          // 纯预估，不落盘
run_job(plan_id) -> job_id        // 开始执行，输出到 _optimized/_clean
pause_job / cancel_job
undo_job(job_id) -> restored      // 输出移到隔离区
job_report(job_id) -> Csv/Json
```

## 7. 验收标准

1. 从选目录到看见预估值 **不超过 2 秒**（不能等扫完才算）。
2. 预估体积与实际偏差 **< 25%**。
3. 任意一次执行可 **1 次点击撤销**，原文件一个字节不变。
4. 中途取消不产出半截文件。
5. 失败文件必须给出可读原因，不能只显示「失败」。

---

## 8. 不做的事

- 不做批量裁剪 / 拼接 / 加字幕（超出「优化」范畴）。
- 不做自动画面分析（智能码率分配），v1 只按预设。
- 不做硬件加速默认开启（实测更慢）。
